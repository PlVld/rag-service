## [Unreleased]

### Добавлено

- **OpenAI-совместимый API эмбеддингов (vLLM и др.)**
  - Помимо TEI (`POST /embed`) поддерживается `POST /v1/embeddings` с
    Bearer-ключом; формат выбирается автоматически (`auto`: openai при заданном
    ключе, иначе tei) или явно через `EMBEDDINGS_API_STYLE`
  - Новые переменные: `EMBEDDINGS_API_STYLE`, `EMBEDDINGS_API_KEY`,
    `EMBEDDINGS_API_MODEL` (имя модели в API, у vLLM — `bge-m3`)
  - Health-проверка и определение размерности работают для обоих форматов;
    ошибки API пробрасываются с телом ответа

- **Гибридный exact-поиск по ключевым словам и фразам**
  - `POST /v1/documents/search`, `search_documents_tool` (MCP),
    `POST /v1/categories/search` и `search_categories_tool` (MCP) получили
    необязательные параметры `exact_phrases` (до 10 слов/фраз) и
    `phrase_mode` (`any` — достаточно любой фразы, `all` — все)
  - Документы: точный поиск по полнотекстовому индексу `raw_text`
    (WORD-токенизатор, lowercase, phrase matching); совпадения объединяются
    с семантическими, дубликаты схлопываются, результат сортируется
    exact-first (затем по числу совпавших фраз и score)
  - Категории: точный поиск по `category_path` по расширенному пулу
    семантических кандидатов (`limit × 5`, не более 200)
  - Точные совпадения не отбрасываются параметром `min_score`
  - В результатах у точных совпадений есть `exact_match` и
    `matched_phrases`; MCP-вывод помечает их `exact_match=true` /
    `matched_phrases=...`, категории — `[exact]`
  - `scripts/create_text_index.py` создаёт индекс `raw_text` на существующих
    коллекциях (по умолчанию dry-run, `--apply` для создания); новые
    коллекции получают индекс автоматически в `_ensure_collection`
  - Индексы созданы на рабочих коллекциях: `1c_integration`, `1С_SSL`,
    `syntx_1C`, `1c_helpdesk`

- **Порог релевантности `min_score` в семантическом поиске**
  - `search_documents_tool` (MCP), `POST /v1/documents/search` и
    `search_categories_tool` (MCP), `POST /v1/categories/search` получили
    необязательный параметр `min_score` (0–1)
  - Результаты с меньшим косинусным сходством отбрасываются; отсечение
    выполняется в Qdrant (`score_threshold`) и повторно после reranking
  - Значение по умолчанию — **0.55** (переменная окружения `SEARCH_MIN_SCORE`);
    `null` в запросе тоже означает значение по умолчанию, `0` отключает порог

- **Лимит вывода иерархии категорий**
  - `get_category_hierarchy_tool` (MCP) и `POST /v1/admin/categories/hierarchy`
    получили необязательный параметр `limit` (по умолчанию 5000) —
    максимальное суммарное количество категорий в ответе; `null` отключает
    ограничение
  - Коллекции обходятся по порядку, пока не исчерпан лимит; при обрезке
    в ответе есть `truncated`, `total_categories`, `shown_categories`,
    а MCP-вывод сообщает, сколько категорий показано из всего

- **Актуализация категорий из перенесённой коллекции**
  - `POST /v1/admin/categories/sync` читает уникальные `category_path`
    из указанной коллекции и идемпотентно создаёт/исправляет узлы в общей
    коллекции `categories` (включая всех родителей)
  - Поддерживает `dry_run` и `include_old_versions`
  - Уровни читаются из `category_levelN`, а не разбираются из `category_path`:
    название уровня может само содержать ` / `; эмбеддинги считаются только
    для отсутствующих/устаревших узлов
  - Существующие категории не удаляются: коллекция `categories` общая
    для нескольких коллекций документов
  - Заодно исправляет `category_id_levelN` в чанках коллекции-источника:
    ID приводятся к детерминированным UUID узлов для их пути (и `category_id`,
    если поле есть). Это устраняет рассинхронизацию, когда после переноса
    коллекции пути категорий совпадают, а ID категорий в чанках — от прежней
    коллекции `categories`
  - В ответе появились `points_scanned`, `points_with_wrong_category_ids`,
    `points_updated`, `sample_wrong_category_ids`; при `dry_run` запись
    не выполняется, но масштаб расхождения виден
  - Точки без `category_levelN` не изменяются: путь из `category_path`
    неоднозначен, если название уровня содержит ` / `

- **Извлечение изображений из документов**
  - Картинки из DOCX/HTML (и PDF при явном включении) сохраняются на диск,
    а в `raw_text` чанков попадают ссылки вида `![Image](/media/...)`
  - Раскладка `{MEDIA_DIR}/{source_id}/{doc_hash[:16]}/images/` — каталог адресуется
    хешем содержимого, повторная загрузка того же файла не дублирует картинки
  - Каталоги устаревших версий удаляются при создании новой версии документа
  - Раздача картинок через `StaticFiles` по префиксу `MEDIA_URL_PREFIX` (без токена,
    чтобы ссылку мог открыть рендерер Markdown; листинга каталогов нет)
  - Ссылки на картинки не разрываются при чанкинге и не попадают в текст для эмбеддинга

- **Описания изображений через OpenAI-совместимый API**
  - Картинки из документов (PDF, DOCX, HTML, отдельные изображения) описываются
    VLM-моделью на внешнем сервере (vLLM, llama.cpp server, LM Studio, Ollama),
    описания попадают в `raw_text` рядом со ссылкой на картинку и индексируются
  - PDF и одиночные изображения описываются штатной стадией Docling
    (`do_picture_description`), DOCX/HTML — пост-обработкой
    (у SimplePipeline-форматов этой стадии в Docling нет)
  - Доступность сервера проверяется при старте сервиса; если сервер недоступен —
    сервис работает дальше, картинки конвертируются без описаний
  - Для HTML включается `fetch_images`, чтобы вместо плейсхолдеров появлялся растр
  - Переменные окружения: `DOCLING_IMAGE_DESCRIPTION_MODEL` (пустая — функция
    выключена), `_HOST`, `_PORT`, `_API_KEY`, `_PROMPT`, `_TIMEOUT`,
    `_EXTRA_PARAMS` (JSON с доп. параметрами запроса, например
    `{"chat_template_kwargs": {"enable_thinking": false}}`)

- **Переработка `/v1/files`**
  - `source_id` всегда вычисляется сервером: `gen(категория_поиска + имя_файла)`
  - `new_category_path`, отличная от `category_path`, перемещает документ между
    категориями: старый `source_id` помечается неактуальным, документ полностью
    переобрабатывается (категория входит в текст эмбеддинга), `prev_source_ids`
    накапливает цепочку перемещений, версия — сквозная
  - `POST /v1/files/lookup` — поиск категорий по SHA256 хешу файла
  - `POST /v1/files/preview/md` и `/preview/md/text` — превью конвертации в
    Markdown до чанкинга и без записи в Qdrant

- **CI**: pytest + сборка Docker-образа, lock-файлы зависимостей GPU/CPU
  (`requirements.lock`, `requirements-cpu.lock`), удалён устаревший `openapi.json`

- **MCP вынесен из `main.py`** в `app/mcp/` (proxy, tools, middlewares), явный
  реестр `TOOLS` вместо discovery через `vars()`, маршруты `/mcp` скрыты
  из OpenAPI-схемы

- **Метаданные чанков в `search_documents_tool`**: в ответ добавлены `source_id`
  документа, номер чанка (при `group=false`) или диапазон номеров (при `group=true`)
  и общее количество чанков в документе

- **Сгруппированный текст чанков** без семантического поиска
  - `POST /v1/documents/grouped-text` — детерминированная выборка по коллекции,
    категориям (с вложенностью) и документам (`source_id`); чанки группируются
    по паре «документ + категория» и склеиваются в порядке `chunk_index`
  - MCP-инструмент `get_grouped_text_tool` — тот же отбор, текстовый вывод
    в формате `search_documents_tool` (идентификатор документа, коллекция,
    категория, номера чанков и общее количество чанков)
  - Инструмент добавлен в `ALLOWED_MCP_TOOLS` в `.env.example`; при явном
    allowlist в окружении его нужно добавить и там

### Исправлено

- **`search_documents_tool`: коллекция и категория в выводе**: в метаданные
  каждого результата добавлены `collection_name` и `category_path` — раньше
  по блоку текста нельзя было понять, из какой коллекции и категории он взят
- **Задвоение `limit` при `group=false`**: `_return_individual_chunks`
  не применял итоговый лимит после дедупликации, поэтому при запросе
  `limit=3` возвращалось до 6 результатов (`limit=6` — до 12). Теперь
  `limit` соблюдается строго и для отдельных чанков
- **Двойная конвертация Markdown от Docling**: `extract_text_from_file` возвращает
  фактический формат текста, и Markdown не проходит повторно через html2text
  (двойная конвертация схлопывала переводы строк, весь документ превращался
  в одну строку-заголовок). В payload разделяются `source_format`
  (как текст реально обработан) и `original_format` (формат исходного файла
  по данным клиента)
- **`category_id_level*`**: общая `apply_category_levels` в utils, перегенерация
  ID при обновлении категорий, удаление протухших глубоких уровней
- **Производительность `get_grouped_text`**: фильтр по категориям перенесён
  в Qdrant (`category_levelN`), `raw_text` читается только для групп, попавших
  в ответ после `limit`, страницы scroll увеличены, коллекции обрабатываются
  параллельно. Выборка по категории на коллекции в 350 тыс. точек ускорилась
  с десятков секунд до десятых долей секунды

### Изменено

- Healthcheck (Dockerfile, Dockerfile.cpu, docker-compose): `timeout` 10s → 30s,
  `start_period` 60s → 180s — старт с загрузкой моделей эмбеддингов дольше минуты
- Убраны CPU-пины PyTorch из `requirements.txt` (GPU-сборка теперь возможна),
  исправлена версия `pymorphy2-dicts-ru`

### Новые переменные окружения

- `DOCLING_EXTRACT_IMAGES` — сохранять изображения из документов
- `DOCLING_EXTRACT_PDF_IMAGES` — извлекать изображения из PDF (требует рендеринга страниц)
- `MEDIA_DIR` — каталог для извлечённых изображений
- `MEDIA_URL_PREFIX` — префикс URL для раздачи изображений
- `MEDIA_BASE_URL` — базовый URL для абсолютных ссылок
- `DOCLING_IMAGE_DESCRIPTION_MODEL` — модель описания изображений (пустая = выключено)
- `DOCLING_IMAGE_DESCRIPTION_HOST` / `_PORT` — адрес OpenAI-совместимого сервера
- `DOCLING_IMAGE_DESCRIPTION_API_KEY` — API-ключ сервера описаний
- `DOCLING_IMAGE_DESCRIPTION_PROMPT` — промпт описания
- `DOCLING_IMAGE_DESCRIPTION_TIMEOUT` — тайм-аут запроса описания (сек)
- `DOCLING_IMAGE_DESCRIPTION_EXTRA_PARAMS` — JSON с доп. параметрами запроса

## [1.2.0] - 2026-08-03

### Добавлено

- **Гибридный поиск с взвешенным RRF**
  - Поддержка Reciprocal Rank Fusion для объединения результатов
  - Настраиваемые веса: `DOCUMENT_WEIGHT` и `CATEGORY_WEIGHT_FINAL`
  - Параметр `ENABLE_WEIGHTED_RRF` для включения взвешенного RRF

- **Группированный поиск документов**
  - Новый эндпоинт `/api/documents/search/grouped`
  - Группировка результатов по `category_path`
  - Агрегация чанков в единые документы
  - Параметр `group` для управления поведением группировки

- **Улучшенная обработка категорий**
  - Автоматическое создание иерархии категорий при загрузке документов
  - Поддержка multiple category levels (`category_level0`, `category_level1`, ...)
  - Категории обновляются инкрементально при загрузке новых документов
  - Поиск категорий с группировкой по коллекциям

- **MCP (Model Context Protocol) интеграция**
  - Кастомный MCP прокси для AI-ассистентов
  - Три инструмента: `search_documents_tool`, `search_categories_tool`, `get_category_hierarchy_tool`
  - Настройка разрешённых инструментов через `ALLOWED_MCP_TOOLS`
  - Аутентификация MCP через `MCP_AUTH_ENABLED`
  - Документация в `docs/mcp_tools.md`

- **Версионирование документов**
  - Поддержка версий документов (`version` поле)
  - Метка `is_latest` для различения актуальных и старых версий
  - Возможность поиска с включением старых версий (`include_old_versions`)
  - Автоматическая пометка старых версий при обновлении документа

- **Reranking результатов**
  - Пересчёт score на основе косинусного сходства с вектором запроса
  - Улучшенное ранжирование после группировки

- **Docling Integration**
  - Поддержка Docling для конвертации документов в Markdown
  - OCR для сканированных документов (Tesseract, RapidOCR, EasyOCR)
  - Распознавание изображений и табличных данных
  - Настраиваемые параметры: `USE_DOCLING`, `DOCLING_OCR_ENGINE`, `DOCLING_DO_OCR`

- **Мониторинг и логирование**
  - Middleware для диагностики запросов
  - Логирование MCP запросов
  - Обработка "Expect: 100-continue" + chunked encoding
  - Diagnostic logger для отладки

- **Новые переменные окружения**
  - `DOCUMENT_WEIGHT` — вес документа в гибридном поиске
  - `CATEGORY_WEIGHT_FINAL` — вес категории в итоговом score
  - `ENABLE_WEIGHTED_RRF` — включение взвешенного RRF
  - `USE_DOCLING` — использование Docling
  - `DOCLING_OCR_ENGINE` — OCR движок
  - `DOCLING_DO_OCR` — включение OCR
  - `DOCLING_IMAGE_DESCRIPTION_MODEL` — модель описания изображений
  - `MCP_AUTH_ENABLED` — аутентификация MCP

### Изменено

- Улучшена нормализация текста для эмбеддингов

### Исправлено

## Символы

- `Added` — для новых возможностей
- `Changed` — для изменений в существующей функциональности
- `Deprecated` — для возможности, которая будет удалена в ближайших версиях
- `Removed` — для больше не существующих возможностей
- `Fixed` — для исправленных багов
- `Security` — для устранения уязвимостей

## Versioning

Проект использует [Semantic Versioning](https://semver.org/lang/ru/) в формате `MAJOR.MINOR.PATCH`:

- `MAJOR` — неразрывные изменения API
- `MINOR` — обратное совместимые добавления
- `PATCH` — обратные совместимые исправления
